# Pacman - Ghosts! More ghosts!

## Description

A complete, playable recreation of the classic arcade game **Pac-Man**, written
in Python with an object-oriented, modular architecture. The player navigates a
maze, eats pacgums while avoiding four ghosts, grabs super-pacgums to turn the
tables and eat the ghosts, and progresses through several levels against a time
limit.

Highlights:

- Mazes generated by an external **A-Maze-ing** package (not ours).
- Configurable gameplay through a commented JSON config file, with robust
  defaults and no crashes on bad input.
- Persistent top-10 highscore system.
- Polished UI rendered with raylib: main menu, in-game HUD, pause menu,
  highscores, controls and game-over / victory screens.
- A cheat menu to make peer review easy.

The game loop follows: **Main Menu → Start Game → Win or Lose → Enter name for
highscore → Back to Main Menu.**

The game is available on itch.io on private: https://mdourdoi.itch.io/42-pacman

## Instructions

### Requirements

- Python **3.10+**
- [`uv`](https://docs.astral.sh/uv/) (used by the Makefile to manage the
  virtual environment and dependencies)
- A Linux/X11 desktop session (the game uses raylib for rendering and `pynput`
  for keyboard input)

### Keyboard permissions (Linux / X11)

Input is captured globally with `pynput`. On X11 you must grant the current user
access to the X server before launching the game, otherwise key presses are not
received:

```sh
xhost +SI:localuser:$(whoami)
```

### Install & run

```sh
make install   # create the venv and install dependencies via uv
make run       # launch the game
```

## Configuration

The game reads its configuration from a JSON file (`config` at the project
root). In addition to standard JSON, **lines starting with `#` are treated as
comments and ignored**.

On any problem the game never crashes: missing keys, wrong types,
out-of-range values are reported with a clear warning and replaced by the
default; **unknown keys are ignored**.

| Key                   | Type  | Default            | Accepted values            |
| --------------------- | ----- | ------------------ | -------------------------- |
| `fps`                 | int   | `60`               | 30–60                      |
| `seed`                | int   | `42`               | any int (level 1 seed)     |
| `width`               | int   | `10`               | >= 10                      |
| `height`              | int   | `10`               | >= 10                      |
| `lives`               | int   | `3`                | > 0                        |
| `gum_val`             | int   | `10`               | ≥ 0 (points per pacgum)    |
| `supergum_val`        | int   | `50`               | ≥ 0 (points per super-pacgum) |
| `ghost_val`           | int   | `200`              | ≥ 0 (points per eaten ghost) |
| `level_max_time`      | int   | `90`               | > 0 (seconds per level)    |
| `frightened_duration` | float | `7.0`              | > 0 (seconds ghosts stay edible) |
| `pacman_speed`        | int   | `10`               | > 0                        |
| `ghost_speed`         | int   | `6`                | > 0                        |
| `num_levels`          | int   | `1`                | >= 10                      |
| `highscore_filename`  | str   | `highscore.json`   | a writable path            |

Example:

```jsonc
{
    "fps": 60,
    "seed": 42,
    "width": 11,
    "height": 11,
    "lives": 3,
    "gum_val": 10,
    "supergum_val": 50,
    "ghost_val": 200,
    "level_max_time": 90,
    "frightened_duration": 7.0,
    "pacman_speed": 8,
    # comments starting with '#' are ignored
    "ghost_speed": 6,
    "num_levels": 10,
    "highscore_filename": "highscore.json"
}
```

## Highscore

Highscores are stored as a **JSON file** on disk (path set by
`highscore_filename`, default `highscore.json`). The file is a list of
`{"name": ..., "score": ...}` objects.

How it works:

- The table is **loaded at game start** and **saved when the game ends** (win or
  lose). On game over the player is prompted to enter a name.
- Only the **top 10** scores are kept, sorted by descending score.
- **Names** are validated to be 1–10 characters, alphanumeric and spaces only.
- **Scores** must be non-negative integers; invalid entries are skipped.
- The loader is **robust to file errors**: a missing file is created and treated
  as empty, and an invalid/corrupt file is ignored rather than crashing the game.
- The current highscores are shown from the main menu.

**Why a JSON file?** It is persistent, human-readable, trivially editable for
testing, requires no external service or database, and maps directly onto the
simple `name`/`score` records we need. This keeps the system dependency-free and
easy to reason about while satisfying the persistence requirement.

## Maze Generation

We **do not** write our own maze generator. Mazes come from the assigned
**A-Maze-ing** package, vendored as a wheel in `packages/` and installed as the
`mazegenerator` dependency. We use it **as-is**; our loader adapts to its
interface, not the other way around.

- The maze is built with `MazeGenerator(size=(width, height), perfect=False,
  seed=seed)`. `PERFECT=False` produces loops and Pac-Man-compatible corridors
  (no dead-end-only mazes).
- **Level 1** uses the fixed `seed` from the config; **subsequent levels** are
  regenerated.
- Each cell exposes its walls as a 4-bit mask (`1` north, `2` east, `4` south,
  `8` west), which matches our `Direction` flags so movement and wall checks are
  simple bitwise operations.
- On top of the generated maze we place a regular pacgum on every walkable cell,
  a super-pacgum in each of the 4 corners, and leave the central cell free as
  the player's spawn.
- If the generator fails, the error is handled cleanly without a traceback.

This lives in `src/instances/map.py` (`Map` / `Cell`).

## Implementation

The game runs a fixed-timestep loop driven by an **Orchestrator**. Each frame it
collects input, updates the engines on the active stack, renders them and
throttles to the configured FPS.

Key points:

- **Screens as engine/renderer pairs.** Every screen (menu, game, pause,
  cheats, scores, controls, quit, score registration) is an `Engine` (logic)
  paired with a `Renderer` (drawing). Screens are kept on a **stack** in the
  shared `GlobalState`; the top of the stack has focus. This makes overlays like
  the pause and cheat popups natural - they are pushed on top of the game.
- **Input.** Keyboard input is read on a background thread via `pynput` and
  translated into abstract events (`EventsEnum`), so engines never deal with raw
  keys.
- **Movement.** Pac-Man and the ghosts move tile-to-tile. Movement is
  accumulated as "progress" each frame and positions are interpolated between
  tiles for smooth rendering, decoupling logic speed from frame rate.
- **Ghost AI** (see `src/engines/game_engine.py`):
  - **Chase** reproduces the original arcade behaviour: each ghost has its own
    *target tile* (Blinky targets Pac-Man, Pinky aims a few tiles ahead, Inky
    uses Blinky's position to pick a point beyond Pac-Man, Clyde chases while far
    away and retreats to its corner when close). At each junction the ghost picks
    the open direction that minimises the distance to its target, never reverses
    unless forced, and breaks ties with a fixed **North → West → South → East**
    priority.
  - **Flee** (when edible) is simply the **inverse** of the chase AI: the ghost
    picks the direction that *maximises* the distance to Pac-Man.
  - There is **no scatter mode on purpose**: the subject asks for ghosts that
    chase with their own AI and flee when edible, so a periodic scatter phase
    would go against the requested behaviour.
  - An eaten ghost becomes a pair of **eyes** that return to its spawn, then
    respawns after a short delay.
- **Cheats.** A cheat menu toggles invincibility, ghost freeze, increased speed,
  extra life and instant level-win, so a reviewer can exercise every feature
  quickly.
- **Robustness.** Configuration and highscore parsing degrade gracefully and the
  entry point wraps execution so the program reports errors instead of dumping a
  Python traceback.
- **Quality.** The code is type-hinted, documented with PEP 257 docstrings, and
  passes `flake8` and `mypy` (`make lint`).

## General Software Architecture

The source lives under `src/`, organised by responsibility:

```
pac-man.py                                                            # entry point -> src.main.main()
src/
├── main.py                                                           # parse config + scores, init window, run orchestrator
├── core/
│   ├── orchestrator.py                                               # main loop, engine/renderer stack, frame timing
│   └── input_handler.py                                              # background keyboard listener -> abstract events
├── engines/                                                          # per-screen game logic
│   ├── engine.py                                                     # Engine (ABC)
│   ├── menu_engine.py                                                # MenuEngine
│   ├── game_engine.py                                                # GameEngine (gameplay, movement, ghost AI)
│   ├── popup_engine.py                                               # PopupEngine (base for overlay screens)
│   │   ├── scores_engine.py                                          # ScoresEngine
│   │   ├── controls_engine.py                                        # ControlsEngine
│   │   └── score_register_engine.py                                  # ScoreRegisterEngine
│   └── region_popup_engine.py                                        # RegionPopupEngine (selectable list popup)
│       ├── pause_engine.py                                           # PauseEngine (+ Konami code -> cheats)
│       ├── cheat_engine.py                                           # CheatEngine
│       └── quit_engine.py                                            # QuitEngine
├── renderers/                                                        # drawing, one renderer per engine
│   ├── renderer.py                                                   # Renderer (ABC)
│   ├── window_handler.py                                             # world<->screen scaling, fullscreen
│   ├── menu_renderer.py / game_renderer.py
│   ├── popup_renderer.py                                             # base popup panel
│   └── controls_/scores_/score_register_/region_popup_ renderer.py
├── instances/                                                        # game objects
│   ├── entity.py (ABC) -> pacman.py, ghost.py
│   ├── map.py                                                        # Map / Cell (wraps the A-Maze-ing maze)
│   ├── gum.py                                                        # Gum / SuperGum
│   └── direction.py                                                  # Direction (bit flags)
├── parsers/                                                          # config_parser.py, scores_parser.py
├── pacman_types/                                                     # vec2.py (Vec2)
└── state/                                                            # global_state.py + enums (EngineFlag, EventsEnum, GhostKind, GhostMode)
```

Relationships at a glance:

- **`Orchestrator`** owns the `WindowHandler`, the shared **`GlobalState`**, the
  `InputHandler`, and a dictionary mapping each `EngineFlag` to its
  `(Engine, Renderer)` pair.
- **Engines** read/write `GlobalState` (events, focus, engine stack, score,
  cheat flags) and never draw; **Renderers** read engine/state data and draw,
  scaling world coordinates to screen pixels through the `WindowHandler`.
- The **`GameEngine`** owns the `Map`, the `Pacman` and the four `Ghost`
  instances; `Pacman` and `Ghost` both extend `Entity`.
- The **`Map`** wraps the external A-Maze-ing maze and exposes movement helpers.
